# Terraform plan

No Terraform exists in the repo today. This document defines the **minimum** infrastructure to prove Entra and the **recommended** layout for later social-login work.

## Design principles

1. **Separate state** for Entra proof env (e.g. `infra/entra-proof/` or `terraform/rd-box/`).
2. **No secrets in tfvars committed to git** — client secrets generated by Terraform go **directly into Key Vault**.
3. Use **`azurerm`** + **`azuread`** providers against subscription `acf84f87-9597-43fd-9994-761c094389fa`.
4. **Reuse** existing `rdbox-rg` and `rgboxtest` storage unless isolation is required.
5. Outputs feed box deployment (authority, client id, vault URI, public web origin).

## Proposed directory layout

```text
infra/
  entra-proof/
    versions.tf          # provider pins, backend config
    variables.tf         # subscription_id, tenant_id, location, public_origin
    main.tf              # module wiring
    keyvault.tf          # Key Vault + RBAC
    entra-app.tf         # azuread_application + password → Key Vault secret
    outputs.tf
    terraform.tfvars.example
    README.md            # apply instructions (human-facing, not AI-only)
```

Backend options:

| Option | When to use |
|--------|-------------|
| `azurerm` backend → storage account `rgboxtest` | Quick start; reuse existing storage |
| Dedicated `rdboxtfstate` storage account | Cleaner separation for team use |

## Resources to create (phase 1 — proof)

### Existing (data sources only)

```hcl
data "azurerm_resource_group" "box" {
  name = "rdbox-rg"
}

data "azurerm_storage_account" "users_tables" {
  name                = "rgboxtest"
  resource_group_name = data.azurerm_resource_group.box.name
}
```

### Key Vault

See [keyvault.md](./keyvault.md). Terraform creates:

- `azurerm_key_vault` (e.g. `rdbox-kv`, region `eastus2` to match RG)
- RBAC: `Key Vault Secrets Officer` for deployer SP / user; `Key Vault Secrets User` for runtime identity
- Secrets populated from Terraform-managed resources

### Entra External ID app registration (`azuread` provider)

Target tenant: `9af8af7b-10ee-4bd5-b71c-20daa8e37878` (CIAM).

| Resource | Purpose |
|----------|---------|
| `azuread_application` | `box-web` (or `box-web-proof`) SPA/confidential client for OIDC |
| `azuread_application_password` | Client secret → stored in Key Vault |
| Redirect URIs | `{public_origin}/api/users/signin-oidc` for each proof/staging origin |
| `azuread_service_principal` | **Required** — the Enterprise Application entry; user flows can only be assigned to a service principal, not a bare app registration |

**App must issue v2 tokens.** External ID (CIAM) rejects v1 access tokens, so `azuread_application` needs:

```hcl
api {
  requested_access_token_version = 2
}
```

**Note:** User flows and social IdPs are often configured in the **External ID portal** or via Graph API. Terraform covers the **application object**; document manual portal steps in [entra-external-id-setup.md](./entra-external-id-setup.md) until Graph automation is justified.

Example redirect URI variables:

```hcl
variable "oidc_redirect_uris" {
  type = list(string)
  default = [
    "https://localhost:5173/api/users/signin-oidc",   # local HTTPS if used
    "http://localhost:5173/api/users/signin-oidc",    # vite dev (proof only)
    # add deployed staging URL when host exists:
    # "https://box-proof.example.com/api/users/signin-oidc",
  ]
}
```

Production proof should use **HTTPS** on a stable host; localhost HTTP is acceptable for dev-only.

### Optional phase 1.5 — hosting

Not strictly required if proof runs on a temporary App Service / tunnel, but recommended:

| Resource | Purpose |
|----------|---------|
| `azurerm_service_plan` + `azurerm_linux_web_app` | Host `users-api` + edge, or separate apps |
| `azurerm_static_web_app` or SWA behind edge | Host `BoxTop.Web` build |
| Application Insights | OIDC failure diagnostics |

If using Container Apps, register `Microsoft.App` provider first (currently **NotRegistered** in RD-Box).

## Outputs (for box deployment)

```hcl
output "entra_authority" { ... }
output "entra_tenant_id" { value = var.tenant_id }
output "entra_client_id" { value = azuread_application.box_web.client_id }
output "key_vault_uri" { value = azurerm_key_vault.box.vault_uri }
output "key_vault_secret_name_client_secret" { value = "auth-entra-client-secret" }
output "public_web_origin" { ... }
```

Runtime reads secret from Key Vault; Terraform output never prints secret value.

## Provider authentication

For local apply:

```powershell
az login
az account set --subscription "RD-Box"
export ARM_SUBSCRIPTION_ID="acf84f87-9597-43fd-9994-761c094389fa"
export ARM_TENANT_ID="9af8af7b-10ee-4bd5-b71c-20daa8e37878"
```

For CI/CD: **workload identity federation** or service principal with:

- `Application.ReadWrite.All` (or app admin on created app) for `azuread`
- `Contributor` + Key Vault RBAC on `rdbox-rg` for `azurerm`

## Apply order

1. Init backend + providers
2. Plan: Key Vault + RBAC
3. Apply: Key Vault
4. Plan: Entra app + password + secret write
5. Apply: Entra resources
6. **Manual:** External ID user flow + link app (portal)
7. Deploy `users-api` with Key Vault references
8. Run proof tests

## What Terraform does *not* do (yet)

- External ID **user flow** creation (portal / Graph)
- **Social identity provider** credentials (Google client id, etc.)
- Keycloak container (local dev only; stays in Aspire)
- DNS / custom domain for `ciamlogin.com` branding

See [social-login-roadmap.md](./social-login-roadmap.md) for IdP automation later.
